# URDF 자산 로딩 v1 — 구현 계약 (2026-09-11)

외형 개편 계획의 **V1 선행 작업**이다. 독립 렌더러 프로토타입(R1–R4b, background v1)에는 자산
로더가 없다. 장면을 코드에서 프리미티브로 만들어 왔고, R3이 예상보다 빨랐던 이유도 그것이다.
V1(표적을 요격기와 같은 기체로 통일)을 **검증**하려면 URDF를 읽어 삼각형으로 바꾸는 경로가 먼저 있어야 한다.

이것은 실험이 아니라 구현이다. 가설도 임계도 없다. 따라서 사전등록이 아니라 계약이다.

## 2026-09-11 개정 — URDF 라이브러리를 쓴다

초판은 표준 라이브러리만으로 파서를 직접 썼다. **그 판단이 틀렸다.** 이 프로토타입의 격리는
"aerial_gym·시뮬레이터·태스크·검출기·정책을 import하지 않는다"는 뜻이지 범용 파서까지 피하라는
뜻이 아니었다. 검증된 동작을 아무도 시험하지 않은 코드로 옮기는 것은 위험만 늘린다.

**기본 백엔드는 `urdfpy`**(+`trimesh`)다. 링크 트리, 순기구학, 재질, mesh 파일과 scale은
라이브러리가 담당한다. 직접 쓴 파서는 **교차검증용으로 남긴다** — 지우지 않는 이유는
`compare_backends`가 둘의 불일치를 목록으로 내놓기 때문이다. 외형 개편 경로의 다섯 자산에서
링크 순서·링크 월드 변환·geometry 파라미터·재질 색이 **전부 일치한다(불일치 0)**.

**라이브러리로 바꾸면서 측정으로 잡은 계약 위반 셋.** 전부 고쳤다.
1. urdfpy는 **limit이 있는 revolute 관절을 받아들이고 영 자세로 평가**한다. 아무도 고르지 않은
   자세가 조용히 로드된다. 이제 거부한다.
2. urdfpy는 **선언되지 않은 material 참조를 기본색으로 대체**한다. 이제 거부한다.
3. 치수가 0인 형상이 렌더러까지 가서 "Degenerate triangle"로 죽었다. 이제 **형상 이름을 말하며**
   거부한다.

**mesh 지원은 라이브러리 덕에 생겼다.** 초판의 거부 규칙은 해제한다(아래 지원 범위 참조).

## 무엇을 만드는가

URDF의 **visual** geometry를 기존 `MeshScene`(정점·삼각형·face별 material·face별 instance)으로
바꾼다. collision geometry는 읽지 않는다. 카메라가 보는 것은 visual이다.

## 지원 범위 — 저장소 실측에 근거한다

저장소의 URDF에서 geometry 태그를 세면 box 1107, cylinder 118, sphere 14, **mesh 3**이다.
mesh를 쓰는 셋(BlueROV, morphy)은 외형 개편 경로에 없다.

- **urdfpy 백엔드 지원**: `<box>`, `<sphere>`, `<cylinder>`, **`<mesh>`(STL/DAE, scale 포함)**,
  fixed joint, 링크당 복수 `<visual>`, visual의 `<origin xyz rpy>`, 중첩·참조 material.
- **builtin 백엔드 지원**: 위에서 `<mesh>`를 뺀 것. mesh는 계약 문서를 가리키며 거부한다.
- **양쪽 모두 거부(fail closed)**: fixed가 아닌 joint, 없는 링크를 가리키는 joint, 순환, 루트 복수,
  모르는 geometry, 비유한 수, 0 이하 치수, 선언되지 않은 material 참조, visual 없는 robot.
  **두 백엔드가 같은 계약을 지키는지 단위 테스트가 양쪽에 같은 케이스를 건다.**

## 고정하는 규약

- `rpy`는 고정축 roll-pitch-yaw다: `R = Rz(yaw) @ Ry(pitch) @ Rx(roll)`.
- 링크의 월드 변환은 루트에서 joint origin을 연쇄한 것이다. joint는 전부 fixed이므로 관절값이 없다.
- **instance = 링크** (문서 순서). 렌더러의 instance_id와 같은 뜻이다.
- **material = URDF material 이름** (첫 등장 순서). 이름 없는 visual은 선언된 대체 material
  `__urdf_default__`(0.5, 0.5, 0.5, 1.0)를 쓰고, 그렇게 처리된 visual 수를 receipt에 남긴다.
- URDF 좌표: 미터. 원기둥은 +Z 축, 원점 중심, 길이 L. 구는 원점 중심. 상자는 원점 중심.
- 삼각형 winding은 **바깥쪽**이다: `cross(p1-p0, p2-p0)`가 형상 바깥을 향한다.

## 색에 대한 명시적 미결 사항

URDF의 `rgba`를 **변환 없이 그대로** base_color로 쓴다. URDF 색은 표시용(sRGB에 가까운) 값인데
이 렌더러의 Lambertian은 base_color를 linear RGB로 다룬다. **즉 색공간 변환을 하지 않는다는 선택을
선언한 것이지, 두 값이 같다고 주장하는 것이 아니다.** 알파는 무시하고 원본 rgba를 receipt에 남긴다.
변환이 필요해지면 선언된 단계로 나중에 추가한다.

## 곡면 분할

**백엔드마다 다르고, 그것이 정상이다.** 일치해야 하는 것은 URDF가 말하는 내용이지 얼마나 잘게
쪼개는지가 아니다. `compare_backends`는 삼각형 수와 정점을 비교하지 않는다.

- urdfpy/trimesh: 라이브러리 기본값. 요격기 2,304 삼각형. 구 r=0.05가 1,280 삼각형에 부피 −0.861%.
- builtin: 모듈 상수 `SPHERE_SEGMENTS=16`, `SPHERE_RINGS=8`, `CYLINDER_SEGMENTS=16`.
  요격기 736 삼각형. 같은 구가 224 삼각형에 −6.26%.

라이브러리 쪽이 더 정밀하고 더 비싸다. **`trimesh` 버전이 바뀌면 삼각형 수가 바뀔 수 있으므로
receipt에 `urdfpy`/`trimesh` 버전과 배열 SHA를 남긴다.** 조용히 달라지지 않고 receipt가 어긋난다.

## 방향 검사 — 볼록과 일반을 구분한다

`convex_outward_violations`는 **볼록 형상에만 유효하다.** 링크 중심을 기준으로 재기 때문에 오목한
표면에서는 정상인 면도 위반으로 센다. 실제로 BlueROV 선체는 88,721건을 보고하는데 전부 무의미하다.

일반 표면에는 `orientation_report`를 쓴다: **열린 모서리 0 + winding 불일치 모서리 0 + 부호 부피 > 0**.
이 셋은 오목해도 성립한다. 다섯 자산은 전부 통과한다. BlueROV는 열린 모서리 4,854개, 불일치 312개로
**통과하지 못하는데 이것은 출하된 STL의 성질이지 로더의 결함이 아니다.** 보고하되 막지 않는다.

## 검증

- CPU 단위 테스트: 파싱, 변환 연쇄, rpy 규약, 분할, 방향(볼록/일반 구분), 결정성,
  거부 경로 전부를 **두 백엔드에 같은 케이스로** 건다. 그리고 `compare_backends`가 다섯 자산에서
  불일치 0임을 고정한다.
- **부피 수렴 검사**: 분할한 구·원기둥의 부피가 해석값에 선언된 오차 안에서 수렴한다.
  이것이 분할이 실제로 그 형상을 만들었다는 가장 강한 증거다.
- GPU 기술 smoke: 실제 요격기 URDF를 읽어 렌더하고, 링크와 material이 화면에 보이는지 확인한다.

## 이 작업이 말하지 않는 것

렌더링 품질, shortcut 감소, 학습 성능에 대해 아무 주장도 하지 않는다. V1의 자산 교체 자체도
아직 하지 않는다. 이것은 그것을 **검증할 수 있게 하는** 도구다.
