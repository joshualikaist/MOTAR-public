# 실제 시뮬레이터에서 표적 외형을 재보니 — V1은 검출기에 도달하지 않는다 (2026-09-12)

도구 `tools/probe_target_appearance_in_sim.py`, 원자료 `raw.json`.
측정만 하는 기술 검증이다. 사전등록된 가설도 임계도 없고, 학습이나 정책 갱신도 하지 않는다.

**후속 감사 — PARTIAL_EVIDENCE.** 아래 숫자는 독립 재계산됐으나 전체 궤적·영상 동일성이나
실행 출처의 완전성까지 확인된 것은 아니다. `raw.json`은 보존했다.
[AUDIT.md](AUDIT.md)에 근거 범위, 회귀 실패, CPU 재계산 방법을 기록한다.

후속: 당시 one-link 회귀 실패는 `5cea0e4`에서 수정됐고 전체 테스트로 재확인했다
([현재 상태](../../docs/repository_followup_2026-09-12.md)). 아래 probe와 당시 보고 이력은
보존하며 검출기 입력 개선이나 완전한 실행 출처가 새로 입증됐다는 뜻은 아니다.

## 왜 돌렸나

V1(표적을 쿼드로터 실루엣으로 교체)은 **격리된 렌더러 프로토타입에서만** 검증했다. 그것은
Isaac Gym이 이 자산을 싣는지도, 검출기의 Warp 카메라가 그 실루엣을 보는지도 말해주지 않는다.
프로토타입에서 잰 **투영 면적 41% 감소**가 실제 검출기 경로에서도 같은지는 V4 설계를 좌우한다.

## 결과 — 두 가지가 나왔고 둘 다 예상과 다르다

### 1. v3는 처음에 아예 로드되지 않았다

`aerial_gym/assets/warp_asset.py`가 **링크별** 이름 목록을 **메시별** 카운터로 인덱싱한다.
즉 링크당 메시 하나를 가정한다. v3는 한 링크에 visual 13개였으므로 첫 프레임을 그리기도 전에
`IndexError: list index out of range`로 죽었다.

공유 시뮬레이터 코드를 고치는 대신 **자산을 요격기와 같은 구조로 바꿨다** — visual 하나당 링크
하나, fixed joint로 연결, 추가 링크는 질량 0에 collision 없음. 이 자산 클래스는
`collapse_fixed_joints`가 켜져 있고 요격기 URDF가 이미 같은 모양이라 로드된다는 것이 입증돼 있다.
**base_link의 inertial과 collision은 그대로다.** 바꾼 뒤 실제로 로드된다.

### 2. 저장된 검출 마스크의 **픽셀 수**가 같았다

당시 보고는 32환경 × 120스텝이다. 원자료에는 각 arm의 거리와 픽셀 수만 3,840개씩 저장돼 있다.
동일 인덱스의 거리·픽셀 수가 전부 일치한다. env/frame ID, pose, mask, RGB는 저장되지 않았으므로
전체 궤적이나 이미지가 동일한 완전한 paired experiment라고 단정하지 않는다.

| 거리 구간 | n | v2 중앙값 px | v3 중앙값 px | 면적비 |
|---|---|---|---|---|
| 4–5 m | 1,196 | 18.0 | 18.0 | **1.000** |
| 5–6 m | 1,804 | 6.0 | 6.0 | **1.000** |
| 6–7 m | 840 | 6.0 | 6.0 | **1.000** |

쌍 전체 3,840표본에서 면적비 중앙값 **1.000**, 사분위 범위 **[1.000, 1.000]**이다.

## 원인 — 검출기는 URDF 메시를 보지 않는다

`navrl_detector.py`의 마스크 커널은 **해석적 형상에 광선을 교차**시킨다. 구(`target_radius`) 또는
oriented box(`target_half_extents = wp.vec3(0.14, 0.14, 0.06)`, 소스에 하드코딩)이고, 막대 메시에
가려졌는지만 `mesh_query_ray`로 확인한다. **표적의 visual geometry는 이 경로에 들어가지 않는다.**

이는 **현재 foreground proxy가 visual silhouette를 직접 사용하지 않는다는 소스 근거**다.
가림 검사에는 scene mesh가 들어가므로 어떤 장면·어떤 visual 변경에도 마스크 전체가 불변이라고
일반화하지 않는다. 이번 원자료에서 확인한 것은 저장된 픽셀 수의 일치다.

## 이것이 계획에 대해 뜻하는 것

- **이번 probe에서는 V1 변경에 따른 픽셀 수 변화가 관찰되지 않았다.** 기본값은 v2지만,
  당시 새 v3 자산은 one-link 계약/테스트와 충돌했다. "깨진 것은 없다"는 당시 문장은
  철회하며, 이후 테스트 충돌 해소는 위 후속 기록과 구분한다.
- **프로토타입의 41% 면적 감소는 별도 입력 경로의 결과다.** 현재 detector 입력이 바뀌었다거나
  형상 효과·색 shortcut 감소가 측정됐다는 근거로 쓰지 않는다.
- **후속 작업은 우선 근거 정리다.** 독립 renderer와 통합 simulator의 결과 계보를 분리하고,
  빠진 provenance와 계약 불일치를 명시한다. 이 probe가 새 통합 실험이나 정책 실행 권한을 열지 않는다.
- 감사에서 나온 `0.283` 대 `0.28` 불일치가 여기서 구체화된다. 접촉은 URDF 상자(0.283)를 쓰고
  검출기는 하드코딩된 `0.14` 반치수(0.28)를 쓴다. 같은 표적에 대한 두 개의 기하다.

## 측정 방법에 대한 기록

첫 두 번의 실행은 **모든 표본에서 0픽셀**이 나왔다. 원인은 자산이 아니라 두 가지였다.
행동을 0으로 줘서 카메라가 표적을 향하지 않았고(방위 오차로 확인), 고친 뒤에도
`last_pixel_count`를 읽고 있었는데 그것은 검출 경로의 게이팅 후 개수라 `target_mask`에
48–55픽셀이 있는 동안에도 0이었다. **`target_mask`를 직접 세도록 고쳤다.**
그럴듯해 보이는 필드 이름을 확인 없이 쓴 것이 원인이다.
