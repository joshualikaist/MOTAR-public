# D6 — 움직이는 강체 메시의 광선 교차 타당성 (2026-09-12)

사전등록 `PREREGISTRATION.md`(커밋 b3e157c, 실행 전). 벤치마크 `benchmark/benchmark.json`,
시퀀스 `sequence.json`. 구현 `tools/renderer_validation/dynamic_mesh.py`,
참조 `tools/renderer_validation/reference_raycast.py`, 게이트 `tests/test_dynamic_mesh_raycast.py`.

**독립 그래픽스 질문 하나만 다룬다.** 검출기·연관·정책·태스크에 연결하지 않았고, 그 어느 것에
대해서도 주장하지 않는다.

## 판정

| | 결과 |
|---|---|
| **F1** object-local 광선 변환이 정확한가 | **예.** C1–C5 전부 통과 |
| **F2** 매 프레임 BVH 재구성 없이 처리되는가 | **예.** 자세만 바꿀 때 메시 id와 정점 버퍼 포인터가 불변 |
| **F3** 학습 해상도·배치에서 실용적인가 | 128장면 160×90에서 질의 **0.705 ms**, 추가 **+0.245 ms** |
| **F4** 해석적 프록시 대비 추가 비용 | **1.53배** (0.460 → 0.705 ms) |
| **통합 판정** | **`INCONCLUSIVE`** |

**판정 근거를 그대로 적는다.** 사전등록한 구간은 1.5배 이하 `INTEGRATION_WORTHY`,
1.5–3.0배 `INCONCLUSIVE`, 3.0배 초과 `TOO_EXPENSIVE`다. 결정 셀의 실측 비율은 **1.5338**로
경계 바로 위다. **임계를 옮기지 않았다.** 절대 증가분이 0.245 ms로 작다는 것은 독자가 알아야 할
사실이지만, 그것으로 판정을 다시 정의하지 않는다.

## 정확성 — 게이트 다섯

| | 검사 | 결과 |
|---|---|---|
| C1 | 평행이동이 거리를 옮기는가 | 통과. 모든 광선에서 부호가 맞고 크기가 오프셋과 일치 |
| C2 | 회전이 hit 패턴을 바꾸는가 | 통과. 비대칭 형상 90° 회전에서 5% 초과 픽셀이 바뀜 |
| C3 | **역변환 동등성** | 통과. 깊이 최대차 < 1e-5 m, 법선 정렬 < 1e-4 |
| C4 | 법선 변환 | 통과. 단위 길이 1e-5 이내, 전부 카메라를 향함 |
| C5 | BVH 재구성 없음 | 통과. 자세 5회 변경 후에도 서명 불변 |

**C3의 참조는 따로 썼다.** numpy Moller-Trumbore 완전탐색이며 BVH도 Warp도 쓰지 않고,
**광선 대신 메시를 world로 옮겨** 교차한다. 같은 변환 코드로 자신을 검증하면 아무것도 확인되지 않는다.

정적·동적 분리도 확인했다. 벽 뒤의 물체는 보고되지 않고(`source==1`만), 앞의 물체는 이긴다.
하나의 `mesh_ids`에 동적 물체를 넣지 않으므로 자기 자신을 가리는 문제가 생기지 않는다.

세 arm이 **한 커널 안에서** 돌아 동적 물체 처리만 다르다. 질의 시간만 측정한다(중앙값, ms).

546 MiB(1장면 160×90)에서 2,013 MiB(128장면 480×270)까지 늘었다.

## 최종 실행 전에 발견한 측정 결함 셋

개발 로그가 아니라 결과의 일부다. 셋 다 **그럴듯한 숫자를 냈고**, 고치지 않았다면 그 숫자가
결론이 됐을 것이다.

| | 무엇이 잘못됐나 | 그때 나온 숫자 | 어떻게 드러났나 |
|---|---|---|---|
| 1 | 해석적 프록시 arm을 **numpy로 host에서** 계산했다. GPU 메시 대 CPU 프록시를 비교한 셈이다 | 메시가 프록시의 **0.61–0.77배**, 즉 "메시가 더 싸다" | 비율이 1보다 작은 것이 물리적으로 말이 안 돼서 코드를 되짚음 |
| 2 | `cast()`가 **호출마다 광선을 GPU로 다시 올렸다**. 128프레임 160×90에서 호출당 22 MiB | 128×160×90에서 **44 ms**, 생산 기하 패스(~3 ms)의 15배 | 절대값이 기존 렌더러보다 한 자릿수 느려 원인을 찾음 |
| 3 | 게이트 픽스처가 카메라에서 너무 멀었다. 3 m에서 0.6 m 상자 | 유효 픽셀 **24–26개**, 게이트 넷이 표본 부족으로 실패 | 게이트가 실패하며 즉시 드러남 |

1번과 2번은 **틀린 채로 통과했을 결함**이다. 1번은 "동적 메시가 프록시보다 싸다"는 반대 결론을,
2번은 "학습 규모에서 비현실적으로 비싸다"는 반대 결론을 낼 뻔했다. 3번만 게이트가 스스로 잡았다.

수정 방향도 기록한다. 1번은 프록시를 **같은 커널 안의 해석적 구**로 옮겼다(생산 검출기와 같은 처리).
2번은 광선·자세·출력 버퍼를 디바이스에 올려두고 **질의만** 재게 했다. 3번은 카메라를 옮겼고
**허용오차와 50쌍 하한은 그대로** 뒀다.

### 위 표의 1번과 2번, 자세히

**프록시 arm을 CPU numpy로 구현했었다.** 그래서 메시가 프록시보다 빨라 보였다(0.6~0.8배).
그것은 메시 질의에 대한 발견이 아니라 host 왕복 측정이다. 프록시를 같은 커널 안의 해석적 구로
옮겨, arm 사이의 차이가 동적 물체 처리뿐이 되게 했다.

**호출마다 광선을 GPU로 다시 올리고 있었다.** 128프레임 160×90에서 호출당 22 MiB다. 첫 절대
수치(128×160×90에서 44 ms)는 대부분 그 전송이었다. 광선·자세·출력 버퍼를 디바이스에 올려두고
질의만 재도록 고쳤다. **비율은 영향받지 않았지만**(양쪽이 같은 전송을 지불) 절대값은 F3에
답할 수 없었다.

정확성 게이트 넷도 첫 실행에서 표본 부족으로 실패했다. 카메라가 0.6 m 상자에서 3 m 떨어져 있어
24~26픽셀만 맞았다. **프레이밍 문제이므로 카메라를 옮겼고 허용오차와 50쌍 하한은 그대로 뒀다.**

## 성공해도 말하지 않는 것

주장할 수 있는 것은 **딱 이것뿐이다**:

> object-local 광선 변환으로 동적 강체 메시를 정적 BVH 재구성 없이 렌더링하는 독립 경로가
> 정확성 게이트를 통과했고, 해석적 프록시 대비 결정 셀에서 1.53배 비용이며 사전등록 구간상
> `INCONCLUSIVE`다.

**주장하지 않는 것**: 실제 검출기가 형상을 사용한다, 색 지름길이 줄었다, 인지가 좋아졌다,
연관·정책·태스크 성능이 바뀐다.

## 이 실험이 선행조건으로 두지 않은 것

`0.283` 대 `0.28` 기하 계약 불일치는 여기서 다루지 않았고 프로토타입은 기존 기하 의미를 보존한다.
`GEOMETRY_CONTRACT_DECISION_PENDING`으로 남으며 **본 검출기 통합 전에만** 결정하면 된다.
타당성 결과를 보기 전에 선택지 중 하나를 고르지 않는다.
